本目录存储了大量缓存文件, 用于加速 AST 分析.

## 为什么需要缓存

Tree Shaking 使用链式解析, 来分析所有可能关联的 ".py" 文件, 这个数量是庞大的, 可能有几千到几万个文件.

磁盘读取, AST 解析是一个耗时的事情, 特别是在这个数量规模下. 此外, 我们还使用 "影响因子" 的概念来影响分析过程, 更改一次影响因子, 设计的是几千到几万个文件的重算, 因此增长规模非常夸张, 也因此, 我们需要一个好的缓存目录结构, 避免单个目录成倍地增殖.

## 缓存目录结构

```
tree_shaking
|= _cache
    |= watch_files
        |- _readme.md                   # 本文件.
        |= <source_type>-<source_id>    # 影响源
            |- revision.pkl             # 影响源的版本号
            |= <impact_factor_id>       # 二级影响因子
                |- revision.pkl         # 二级影响因子的版本号
                |- <thread_name>.pkl    # 缓存文件
                |- ...
            |= ...
        |= ...
```

影响源的缓存文件夹名称由两个部分组成:

- `source_type`: 影响源的类型, 目前有 "0/1/2/3" 四种类型, 下面详细介绍:

    - "0": 由固定字符串创建的影响源, 只要字符串不变, 则不会重建缓存.
    - "1": 由文件触发的影响源, 当文件的 mtime 发生变化, 则会重建缓存.
    - "2": 由文件夹触发的影响源, 当文件夹的 mtime (递归检查子文件 mtime) 发生变化, 则会重建缓存.
    - "3": 由前三者混合的影响源, 当任意一个因子的 mtime 发生变化时, 都会重建缓存.

- `source_id`: 影响源的唯一标识符, UUID4.hex 格式.

## 数量规模

`source_type=0` 的规模很小, 可能只有几十个此类文件夹.

`source_type=1` 的规模非常大, 大概在几千到几万的水平, 且一开始增长速度很快, 后面会快速放缓, 最终会以极慢的速度增长.

`source_type=2` 的规模相对较小, 可能在几百的水平.

`source_type=3` 的规模与 `source_type=2` 相当.
